## 五、GPT 审查四处缺陷修复（2026-09-21）

审查结论「暂时不能上线」指出的四处问题，逐条修复并复验：

### D1 聊天误改岗位状态（「教我怎么谈薪」→谈薪中）
- `inferStageIntent` 增加疑问/假设/求教守卫：句中含「怎么/如何/教我/如果/万一/吗/呢/？」等一律不判为已发生的动作（完全保守：混合句宁可漏判，因有确认步骤兜底）。
- 服务端 `/api/coach/agent` 不再自动写库：只返回 `stageSuggestion`；对话下方出现确认条「听起来你已经『XX』了——只有你点头我才改」，点「更新状态」才推进，「先不」即忽略。
- 测试：stage-intent 新增「求教/假设句永不推进」组（教我怎么谈薪 / 如果我拿到 offer 呢？ / 谈薪要注意什么 / 万一没通过怎么办 → 全部 null）。

### D2 引导复盘材料未接通 + 假「已保存」
- `guideReview` 改为 async：live 模式先 `await` 快照写入 `/api/coach/snapshots`，**确认成功才**提示「素材已保存」并开启辅导；失败如实播报「保存失败——素材还留在输入框里」且不清空输入。按钮期间显示「正在保存素材…」并禁用。
- 素材真实进上下文三处：辅导首条 prompt（内嵌原文 ≤1500 字）、操作日志摘要、服务端面试台账（`interviewLedgerFor` 把「待引导复盘」的 `sourceNotes` ≤800 字作为原始素材注入，规避 metadata 900ms 同步竞态）。
- 浏览器实测（demo）：填素材→点击→按钮态正确、announce 出现「素材已保存，导师会在右侧带你一步步复盘」、输入框随后清空（清空以保存成功为前提）。

### D3 简历拖拽只是视觉排序
- 拖拽落点即调用 `reorderResumeText` **改写真实 `resumeText`**（分块携带章节标题，重建时对连续同标题去重，合成「其他调整」块不参与重排）；组件不再有本地顺序 state。
- 保存（localStorage/云端 PATCH 防抖）、质检、冻结、导出（`ResumeExport baseText=resumeText`）全部自然跟随新顺序。
- 测试：resume-blocks 新增 reorder 三用例（整节移动内容无损、项目卡移动标题不重复、未知 id/原地移动返回 null）。
- 浏览器实测（demo，注入多节简历后真实拖拽）：「数据看板」拖到「智能客服工作台」之前后，卡片顺序在重渲染后保持新序（证明文本已改写而非组件 state），announce「已按新顺序改写简历，导出与检查都会用这个顺序」。
- **订正（第二轮复查）**：本条当时只验证了「顺序变了、整节移动无损」，但分块器会把「技能：Python」这类带冒号的内容行误判为章节标题、且「有标题无内容」的悬空标题在重建时被丢弃——真实复现是**拖拽会丢行**。修复与不变量测试见第六节 F1；冻结后拖拽仍导出旧产物见 F2。

### D4 经济模型静默换贵

- 测试：release-honesty 新增三组（flash 数字命名可换 / 全高阶返回 null / 无 flash 时取普通 cheap）。

## 六、第二轮复查三处上线阻断修复（2026-09-21）

第二轮复查确认 650 用例全过，但指出三处上线阻断：拖拽丢内容、导出可能仍是旧顺序、确认状态≠保存成功。本轮补的测试全部断言**数据不变量**（每行都在、失败回滚、导出恒等于当前正文），不再只看界面顺序。

### F1 拖拽丢简历内容（复现行：「技能：Python」拖动后消失）
- 根因两条：`classifyHeader` 把「技能：Python」这类冒号后带内容的短行误判为章节标题（内容被当作空节丢弃）；任何「有标题、无正文」的节在 `flush` 提前 return，标题行不进任何块，重建时消失。
- 修复：`lib/opportunities/resume-blocks.ts` 冒号守卫（`分类标题` 冒号后仍有文字则不是标题）+ 悬空标题独立成块（`flush` 空节也保留标题行）。
- 测试（round-trip 不变量）：`resume-blocks.test.ts` 新增「重排不丢内容」describe——含「技能：Python」尾行的简历，split 后该行必须存在于某块；拖动项目块后**逐行**断言原文每个非空行仍在新 `resumeText` 中；末尾孤零零标题、连续标题无内容均不丢。
- 浏览器复现（demo mock 注入 GPT 原场景简历）：拖「数据看板」到「智能客服工作台」前，顺序真实改写且页面全文包含全部 8 个原文行，「技能：Python」不再消失。

### F2 冻结后拖拽，PDF 仍读旧产物
- `Opportunity` 新增 `frozenStale` 标记：`applyReorderToOpportunity`（拖拽统一入口）在已有冻结产物（`applicationQuality.artifactId`）时改写正文的同时置 `frozenStale:true`。
- 三处消费：`resumeProgress` 把 stale 视为「检查未通过」，动作强制回 `check`→`freeze`（提示语明确「旧投递版本已过期」），已冻结版本号不回退；`ResumeExport` 在 stale 时**不传 artifactId**，导出一律用当前正文（宁可不导旧版，不再出现界面新序/PDF 旧序）；重新冻结成功时清除 `frozenStale`。导出标签同步显示「投递版本 V2（已过期：正文在冻结后又改过）」。
- 测试：`resume-progress.test.ts` 新增 stale 用例（action=check、steps=[done,active,waiting]、hint 含「已过期」、frozenVersion 仍为 2；恢复后回到 export）；`resume-blocks.test.ts` 新增 `applyReorderToOpportunity` 三分支（有产物→置 stale、无产物→不置、no-op/未知 id→changed:false）。
- 复验边界：冻结→拖拽→导出的端到端链路需登录态与质检产物，demo 无法人工走通，由上述 jest 覆盖；拖拽触发 `frozenStale` 的 UI 播报文案已在 demo 拖拽中核对。

### F3 确认状态不等于保存成功
- 新增纯函数 `lib/opportunities/stage-save.ts::commitStage`：live 模式下 **PATCH 返回 ok 才提交新阶段**，失败（含 500、非 JSON、网络异常）时返回**原列表**（引用相等，界面回滚）+ 错误原因。
- 确认条按钮改为 `await` 保存结果：成功才关闭确认条并记日志；失败时确认条保留可重试、按钮期间「正在保存…」，announce 明确播报「状态没有保存：<原因>——岗位仍是「旧状态」」。
- 测试：`stage-save.test.ts` 5 用例——成功提交（断言 PATCH 收到含新状态的整份岗位）/ `{ok:false}` 500 → 列表引用回滚 / 抛异常 → 回滚+「网络异常」/ demo 本地直接生效不发请求 / 岗位不存在不误提交。
- 复验边界：真实 500 回滚在 demo 无法人工触发（需登录），由 jest 断言回滚引用相等覆盖。

### 静态 `cheap` 标签 ≠ 真实价格（复查附带观察，本轮未动）
- `MODEL_CATALOG` 的 tier 是手工维护的静态表，只能保证「同档内替换」，不能保证网关实际计价一定更便宜。要闭环需接价格接口或定时核对，列为后续项，不计入本轮完成。

## 七、Codex 收口修复与发布门禁（2026-09-21）

第三次复审发现第六节仍未覆盖完整连续操作，本轮已修复：

1. **F2 检查与冻结独立失效**：原实现只有冻结成功能清除 stale，却因 stale 永远只能检查，形成死循环。增加 `resumeCheckStale`；拖拽使检查失效，重新检查通过只恢复检查有效性，`frozenStale` 仍保留到重新冻结，动作可走 `check → freeze → export`。检查返回时若正文或建议已发生变化，不把旧检查应用到新材料。
2. **F3 不回写旧列表**：失败保留最新界面数据；成功用函数式更新，只合并目标岗位的阶段字段，不覆盖请求期间的简历编辑/新增岗位，不恢复已删除岗位。云端阶段确认使用独立 `stageUpdate`，只更新 stage 与时间、按用户归属过滤并检查实际命中。后台自动同步使用 `preserveStage`，不再携带旧 stage 覆盖已确认的新状态；读取时从真实 stage 推导状态标签。
3. 新增连续操作、延迟成功/失败、删除期间返回、权限过滤、实际未命中、后台保存不写 stage 等回归用例。保留原 POST 路由测试。
