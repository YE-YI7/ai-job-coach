## 查到了什么

来源批次 `b195477e-ea07-4b4e-bb73-f5861458a80a` 已封账，实际 31 调/保守 ¥1.0357695。本轮只读取四条完整流程的真实消息与旧输出，不调用其付费 client。

1. **25 条被 HR 说成 25 个百分点，作者又照搬。** 关闭搜索组 `22179633-7c20-43ae-858a-8fe202ea99a6` 的原稿是“同一批 120 题，带引用且版本正确的回答 71→96 条”。+25 条成立；同题集比例差是约 +20.83 个百分点。错误 25 个百分点首次出现在 HR 点评，之后出现在 mentor；不是程序算出来，也不是原材料确认过的事实。
2. **词面疑点混进了模型的核源通道。** `f6-review-references.ts` 把原 UI 检查器的 `wording_not_found` 等 `.notices` 同时复制进 `noticeEvidence` 和位置条目。即使免责声明说“非判错”，HR 仍拿“原文没有提升/迭代这个词”作为否定理由。原稿确有每周数据核对→发现重复提交→前置已有工单提示的行为，不能仅因用了抽象词就说没有迭代。
3. **HR 意见混进了成功保存回执。** 原生 `write_output` 路径直接把 `hrReview`、返修指令、核源上下文追加到 `{saved:[...]}` 工具结果。普通正文路径又把它作为 user 消息发送。同一份未核实的外部点评，随写稿方式不同而带上不同权威身份；原作者返修时看到的是“保存成功＋点评”复合回执。
4. **HR 并非没拿到完整原稿。** 本批 HR 已有单独可读的 resume/facts/JD/candidate，不能把所有错误归因为漏传资料。程序提供可疑词面暗示、点评身份混杂是已证实的接入缺陷；它们是否造成全部语义错误仍未识别，不能从 Trace 推出模型内心原因。

并非所有 HR 建议都错：保留 3 客户试点范围、还原指标中的引用/版本限定、区分协作和管理仍是有效核源方向。“提升效率”与“同批回答数量增加”也不是同一主张，前者若无测量仍需谨慎。不能为了避免误拦而取消这些检查。

另保留 A 组新增“非检索能力不足/叫停开发”、无 JD 基线辅导建议“知识库同步有少量更新”的失败；它们不是已确认事实。**有条件地开头，不会让一条无出处的过去式变成可教用户背诵的经历。**

## 只改了三处运行代码

- `f6-review-references.ts`：给模型的证据引用只含原文位置、字面源文、结构对应，不再携带 UI 词面/未命中结论。原始 notices 完整留在 `sourceComparison` 和用户原有高亮提示中；没删除事实保护或把提示视为已通过。
- `f6-hr-review.ts`：新增同一现有 HR 会话的 `authorHandoff` 数据传递方法。原点评逐字放在标注 `independent_hr / unverified_advice_not_user_fact` 的独立 assistant 消息；既有返修职责和源文另走 host 数据消息。复用 HR 实际审过并已快照的原稿、补充、JD、当前稿（若有）、首稿，带同稿哈希，给原作者可读核对，不从点评抽取“事实”。返修不会重新从可变的调用方对象拼一份不同源文；返回消息的外部改动也不会污染快照。
- `resume-f6-writer.ts`：原生写文件与直接正文两条路径统一调用该方法；保存回执保持原本含义，不再混入 HR 意见。

没有改 system/B05、HR 提示词或校准例、作者职责文本、模型参数、Memory 内容或检索、工具目录、工具选择顺序、12 作者＋1 HR 上限。没有新 Agent、自然语言/字段解析器、正则语义裁判、自动补数、强迫返修或追加独立审稿。`authorHandoff` 的对象/哈希校验只保证回送的是这次现有记录，不判断 HR 是否语义正确。

原作者可以采纳有据问题、拒绝无据建议、保持正文；状态仍是 `author_revised_not_rechecked` / `author_retained_not_rechecked`，绝不改成质量通过。老断点回执未在本次改造成新的事实；本次回放从首请求重新执行宿主、显式使用旧响应，不宣称迁移完所有历史 checkpoint。
