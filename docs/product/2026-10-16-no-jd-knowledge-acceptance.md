# 无 JD 改稿：知识接入与真实验收

日期：2026-10-16。范围：通用简历改稿的方法召回、修改价值、逐问补充、保存刷新与 PDF。不改用户旧作答、不改左栏、不重做整体 UI。

## 接入

- `selectResumeDraftKnowledge` 从已审阅、active 的编译库取得事实改写、逐步补问、排版交付三篇共享方法。没有 JD、没有机会 ID 或没有相近案例，也能取得适用方法；不是复制外部脚本到服务端。
- 方法、相近案例和既有召回按 ID 去重。相近案例继续要求至少两个本人背景维度，不能拿目标 JD 冒充经历。
- 本人原文、事实与补答先进入上下文，再由真实预算编译器决定保留哪些可选知识。预算排除的知识不得从提示词或日志旁路加回；知识 ID 不能成为经历 `sourceIds`。
- 起草、独立价值复核、保留原文判断都读取实际纳入的同一份方法正文。trace 区分方法候选、实际纳入、预算排除和相近案例；拒绝诊断只保存固定类别，不保存正文或推理。

## 真实测试发现并修复

1. 门店运营首轮产生两条有价值修改，实际 PDF 却漏掉首条 bullet。增加保留原单条列表标记的格式规则，不改事实、不把普通段落强行列表化。
2. 技术课程项目的标题已写明“课程项目”，正文精简时省略重复标签仍被误拦。现在仅允许当前同一、未修改的 Markdown 标题提供限定；其他项目、重复锚点、删除标题仍不能借用或去除标签。
3. 模糊经历加“具体个人交付还没梳理”时，旧检查把“梳理/交付”误认作具体动作。真实模型仅删除备注并加课程标签就通过，未采纳该结果。现把缺口备注与实际动作分开，纯模糊职责必须先补一问，不能以标签小改消耗成功额度；具体普通职责不受影响。
4. 允许对原文独立个人免责声明提出空 `after` 的删除建议，仍需有效引用、独立复核和用户确认。真实贡献、姓名、联系方式、必要阶段限定不走这个通道。起草明确沿用肯定动作，不把“做前端页面”包装为“负责开发”，也不把后端否定责任写回正文。
5. 真实技术样本返回“（删除该条）”而非空 after，独立质检还误把它视作有效删除。未采纳该结果。仅在 before 完全是可删的独立免责声明时将这种明确标签规范为真正空替换；真实贡献对应的删除标签被拒。若主要经历被拦，只剩免责声明删除，也不能记作本轮成功；补有界修复与失败退还回归。
6. 原稿已有独立免责声明时，模型漏掉删除建议会让它继续出现在投递正文。仅在已经提出正文改写、原句唯一可定位、存在预算内本人原文引用时补一条空 after 建议，仍经过独立复核并保持 pending 等用户确认。混有真实贡献、原型未上线状态、业务“未处理工单”、重复锚点均不走此规则，不直接改源文件。
7. H 薄经历样本试图靠删除“本科在读”的“在读”凑精简，独立质检误放行；未采纳。新增在读、预计、肄业、结业、未毕业/未取得学位等学历状态保护，日期范围不能替代状态。路由回归覆盖“正文模糊→教育格式小改且删状态→拒绝该建议→只补一问并释放额度”，不是把所有普通经历都拦住。
