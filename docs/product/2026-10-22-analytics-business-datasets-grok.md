左侧一级导航用业务名，不使用 `turns`、`resumeChat` 或表名。一次只显示当前业务的数据；不把所有图表、用户、对话和说明纵向堆到同一页。三个视角复用详情组件和查询口径，但保留各自选中的日期／筛选状态。

### 通用查询能力

1. 日历可选任一已有数据的过去日期，也可选起止日期；今天／昨天／近 7 天／近 30 天只是快捷项，不能是唯一入口。未来日期禁选。长区间若超资源预算，明确提示并要求缩小，不能暗中换成近 7 天。
2. 业务日按 `Asia/Shanghai`，区间为起始日 00:00（含）至结束日次日 00:00（不含）；今天截至响应的 `asOf`。同次分页冻结 `asOf`，防止翻页时窗口漂移。
3. 按视角提供功能多选、新／老用户、阶段、对话轮数区间、付费相关证据等筛选。能自选显示指标／列、排序、清空；不支持的组合禁用并解释，不能显示一个无效筛选器。
4. URL 保留安全的日期、枚举、用户／会话／Trace ID、排序和分页状态；刷新、返回、复制深链接后状态一致。不得把简历、JD、对话正文放 URL 或浏览器持久缓存。
5. 所有数值、列表、分页总数和下钻使用同一有效筛选集合。不能仅过滤当前载入的 20 行。范围外的“历史累计／最近一次使用”须明确标注，不能悄悄混进本期数据。
6. 数据缺失、尚未采集、截断、错误与真实 0 分开显示。无权限不显示内容；接口失败不渲染 0 人；已达扫描上限不能继续声称全量。

## 3. 业务一：基础数据（按天）

默认今天，可切单日或区间。默认表格按日一行，允许选择功能、来源等受支持维度，不预设只看作者挑好的几个数字。点击人数能进入同日期、同条件的用户集合。

| 指标 | 计算与分母 | 点击后看什么 |
|---|---|---|
| 注册数 | 该日 `users.created_at` 的不同账号数，同一排除规则；不是注册按钮点击数 | 当日注册用户，包括注册后无后续活动者 |
| 活跃用户 | 该日发生有效产品行为的不同登录用户；复用并集中定义现有 `isActivityEvent`，排除诊断、服务端任务、测试及内部行为 | 同口径活跃用户，不能混匿名 UV |
| 某功能使用人数 | 日／功能／用户去重；功能尝试人数与完成／失败人数分开，成功定义用最终业务结果 | 对应用户及其实际行为／结果 |
| 平均导师对话条数 | 用户发送条数与导师回复条数分别列；默认用户发送条数 ÷ 该日有用户发言的账号数，可另选按全部活跃用户平均并显示分母 | 发言用户、消息数和失败／未回复情况 |
| 完成对话轮数 | 一条用户消息及其已保存导师回复算 1 轮；用户发送尝试／已回复／失败分列，按稳定 request／turn ID 去重 | 对应会话，不能用模型调用数或双方消息之和代替轮数 |
| 估算平均用户使用时长 | 先按用户累计可观察活动间隔，再除以当前活跃用户数；沿用相邻行为间隔最多计 5 分钟、超过 30 分钟分访问段的方法，标注方法版本与覆盖率 | 每用户估时、行为点数；单事件只有 0 秒可观察间隔，不代表真实只用 0 秒 |
| 断点／失败分布 | 分开显示最后可观察步骤、明确失败阶段、未完成任务、仍处理中／结果未知；计数单位（日用户／会话／任务）必须显示 | 原事件时间线、阶段码、任务／Trace ID与失败原因码 |

时长必须由完整且已排除诊断的活动流估算，不能先按某功能筛掉中间事件再重算时间。选择某功能时，时长口径为“使用该功能的人当日总估时”，不能误称功能停留时长。跨午夜间隔拆到所属业务日；显示至少两点行为用户占比。现有实现是“每访问段平均”，不能换个标题当“每用户平均”。

活跃定义若确需修改，交出新旧事件规则及对账，标为新版口径，不默默改变历史含义。新／老用户在每个业务日重新判断；区间去重总人数不能直接累加各日 DAU。

UV／PV、来源、次日留存继续作为可选指标／维度。匿名访客不推测绑定账号；采集开始前不补 0。D1 只计算已成熟注册日，分母和未成熟人数明确。来源按已有首触／会话来源分别筛，不混成一个“来源”。

“断点”只表示最后观察到哪一步，不声称用户为何离开。没有点击保存／PDF 事件不能直接推定用户不满意。

## 4. 业务二：会话下钻（用户当天如何使用）

默认今天使用过产品的用户列表：用户 ID、新／老、最近行为、发送／回复／完成轮数、使用功能、当前可观察结果。行点击依次进入用户当天 → 逻辑会话列表 → 具体会话。

注册数下钻是例外：应包含当日注册但没有活动的用户，显示“尚无观察到的使用”，不能为了列表好看丢掉他们。

逻辑会话使用真实 session ID，可跨天；它与估时的“30 分钟访问段”不是同一种会话。默认只看筛选日消息，提供明确的“查看完整会话（跨日期）”；缺历史 session ID 时显示“未关联会话／旧记录”，不按时间接近强行拼起来。

详情按内容切换，而非数据库切换：

- **对话**：用户／导师气泡、时间、消息发送与处理状态；保留结构化 Markdown 渲染，不裸露星号。可分页查看原文，失败的用户消息也显示，不能只展示成功回复。
- **简历**：原稿、生成建议／修改 ID、当前工作稿或有依据的历史版本、修改次数与本轮完成情况。次数区分尝试、生成建议、实际应用、确认保存，不用模型 success 代替交付。列出未完成原因、待补一问、质量检查／返修过程的真实记录。
- **JD／岗位**：用户上传的 JD 原文、岗位来源／链接、关联机会和上传时间。没有历史版本只能标“当前版本”，不得伪装所选日期的原文。
- **面试**：模拟面试与真实面试复盘分开，显示已有问题、回答、导师反馈和留存的评估；缺评分就缺失，不新算 80 分，不调模型补旧记录。
- **阶段判断**：显示留存的用户阶段、导师 `stateObservation`／`stageSuggestion` 与时间、出处；机会阶段和学习阶段单独标示，不把 teaching.stage 冒充求职阶段，不用当前阶段覆盖历史判断。
- **Eval／Trace**：打开与本次消息／任务真正关联的完整 Trace、Agent 阶段输入输出、知识调用、质检、返修、最终交付与已存自评／反馈。已知修改 ID 可直接定位；未捕获 I/O 明确提示，不能用摘要补成原始 Trace。

服务器校验关联链：用户 → 会话／机会／任务 → request／generation → Trace／Eval run → change。只展示确切存在的边；允许一对多，不能把“最新的一次”绑给所有对话。任何 ID 跳转都须重新鉴权和校验归属，不能跨用户泄漏。

Eval 入口必须真实定位目标运行而非仅打开首页列表。当前独立 `eval-lab` 未核到现成 run ID 深链接，Grok 应实现并测试最小定向定位，或复用受保护详情组件。已有 `/admin/evals/records?record=…` 可用于开发归档，但开发记录不能冒充该用户的完整 Trace。没有捕获的普通会话允许明确显示“未捕获 Eval”，保留业务日志。

简历完成状态复用最终交付 v2：running、delivered、partial_delivered、unchanged、needs_detail、blocked、failed、quota_denied、unconfirmed、unknown。再分别显示服务端建议留存、客户端呈现、用户采纳、文档确认持久化、实际 PDF 证据。阶段未知就未知，不能逐级推定成功；`afterprint` 不是实际文件已保存。

## 5. 业务三：按用户（跨会话观察同一个人）

提供明确的“所选期间活跃／全部已注册用户”范围选择。用户 ID 精确搜索可定位无当期活动的用户；仍服从本人／测试排除。默认列表显示 ID、注册日期／注册方式、首次／最近观察使用、选期消息轮数、功能、阶段、简历修改／交付情况、付费证据状态。

- 新用户＝在所选日／区间注册；老用户＝在起点之前注册；注册时间缺失＝未知。按天表则逐日重算；不能仅按“是否首次被埋点看到”判断。
- 注册方式来自可靠账号创建／身份绑定记录；当前手机号已绑定不一定代表手机号注册。缺历史创建方式标未知，不从昵称猜。
- 筛选支持新／老／未知、ID、实际使用功能、已记录阶段、对话轮数最小／最大、付费证据状态，可组合。时间筛选对交互数据有效，累计字段显式标“历史累计”。
- 选中用户先看按日活动／会话列表，再看与业务二复用的详情。能找到今天发了什么、上一使用时间和内容、导师输出、简历改了几次、相应 Eval。最后／上一次必须展示时间及是否超出选期。
- 不新增“用户已流失”标签；只有观察期未再使用。原始内容按需加载，默认列表不倾倒整份简历或联系方式。

### 付费筛选不能造假

现有 `watcha_point_transfers.status=credited` 只证明积分兑换到益职；积分可能来自其他来源，不能当作人民币付款。余额大于 0 也不能证明付费。

先核现有可信支付凭证是否可按稳定账号关联，再决定可用筛选：已确认付款／已兑换积分／已消费付费权益／无已观察记录／未知。可并存的状态不可做互斥假分类。没有真实付款证据时禁用“已付款”条件并说明，不能把未知归为未付费。选期交易与历史累计分开；免费权益只按已有事实记录。

只读服务器安全汇总，不把支付凭据、Token、entitlement ID 或原始账单下发。不调用钱包／兑换／扣费 RPC，不调整任何余额，不根据邮箱／手机号模糊合并账号。

## 6. GEO：本期不做自动运行

本人前提是 TokenDance API 与官网产品的引用逻辑一致才做。当前没有建立这项等价性：

- [Kimi 官方 API 概览](https://www.kimi.com/help/kimi-api/api-overview) 将模型与扩展工具分开，说明模型默认不能直接访问网络／数据库。
- [Kimi 官网 Agentic Search 说明](https://www.kimi.com/en/help/features/search) 描述官网搜索 Agent 自行规划检索、选择来源；开联网也不保证每问都搜。
- 当前 `lib/llm.ts` 的请求构造传 model／messages 等参数，未见联网搜索工具配置。TokenDance 聚合网关能返回模型答案，不证明它复用了官网产品的索引、搜索编排、排序、个性化或引用展示。

据此只能得出“不足以认定两者同逻辑”，不是宣称所有 API 都不能搜索。即使将来 API 能联网，也须独立验证是否对应官网观察目标，不能把 API 测试更名成官网 GEO 评估。

左栏可保留“GEO 研究 · 自动化待确认”，显示上述边界及已有研究位置；不放可用的“开始跑”、不接后台定时任务、不调用收费 API。本期也不做未经授权的官网登录自动批测。

已有 DS 试点是历史研究，不是统一模式下的当前基线：原 25 个入组样本有联网状态／会话污染差异，26 次实际回答中 1 条剔除。保留原记录，不补造剩余样本、不混官网／官方 API／聚合 API 的分母、不以品牌指定题的命中当自然推荐。

将来恢复评测须区分品牌提及率、官网域名引用率、第三方引用率、准确引用率和题目覆盖率。准确引用需要人工或独立审核“来源支持该断言且产品实体正确”，不只是链接 200；记录题集版本、界面类型、模型／搜索配置、实际检索与否、时间、原回答／引用证据、失败／剔除和分母。未知模型版本不能靠网页横幅猜。恢复实施与费用另行审批。

额外建议仅保留待选业务“交付与故障”：跨用户查首次价值、最终交付、失败阶段、恢复与返修；其底层状态本次先在现有三个视角用好，不额外堆一屏新面板。

## 7. 数据与代码对接：先修查询，再做视图

4. `public/eval-lab/app.mjs` 当前入口参数不等于已实现具体运行定位，需验证所加深链。
