## 0. 文档定位

本文件定义"益职 AI 模拟面试"中导师（AI 教练）反馈的**出题规则、单题证据要求、整轮七维可观察标准**，并提供**差反馈与合格导师反馈的 10 组对照**。它是对工作包 A（后端 Harness）的 API 合同的行为规范补充：A 负责让"评分不可伪造"，C 负责让"评分有标准可循"。

三条不可退让的产品原则贯穿全文（来源：PRD 架构决策 1–5）：

1. 面试题、单题反馈、整轮总结必须由**同一份 JD、简历、用户真实回答**驱动，不得用固定假反馈掩盖模型失败。
2. **低信息回答不评分**：返回 `needs_more_input`，说明缺什么、给一个容易回答的追问，保存原回答，不推进题号。
3. **禁止编造经历**：任何反馈、重答提纲、示范内容不得新增用户未说过的经历、数字、职级、团队规模或商业结果。

## 1. 总则：反馈的三个证据来源与优先级

### 1.1 每条结论必须可回溯

单题反馈与整轮总结中出现的每一个判断，都必须能归入以下三类之一（对应 PRD 架构决策 4 与 `InterviewAssessment` 合同）：

| 来源类型 | 含义 | 在反馈中的呈现 | 示例 |
|---|---|---|---|
| 回答中出现的证据 | 用户本轮回答里的事实、数字、决策、行动、结果 | `evidence`（评分时至少 1 条） | "你提到负责召回策略并给出 2 个替代方案对比" |
| 简历 / JD 对照 | 回答与当前岗位简历、JD 要求的一致性、相关性 | 进入 `evidence` 或 `missingEvidence`，并注明对照对象 | "简历写你主导推荐系统，JD 高权重项是排序策略，回答未覆盖" |
| 缺失或冲突 | 回答中缺失的关键事实、与简历/JD 冲突、无法验证的口径 | `missingEvidence` | "转化率提升 30% 未说明口径、时间窗口与归因方式" |

### 1.2 证据优先级（来源：`policies/agent-usage.md`）

1. 用户刚刚提供的真实材料和明确纠正；
2. 当前岗位 JD 与真实招聘流程信息；
3. 用户长期记忆中已确认的事实；
4. 多来源支持的知识文档；
5. 单条公开经历或社区讨论。

**规则**：知识文档只用于补充追问、检查遗漏和校准建议，不得覆盖用户事实，不得把外部案例、职责、数字和结果写进用户回答或反馈。

### 1.3 禁止事项（反馈写作的硬边界）

- 不生成用户未说过的经历与数字；
- 不把面经当作固定题库或招聘承诺；
- 不猜测招聘方心理与面试官意图之外的"他为什么问你"；
- 不把单题表现泛化为长期能力结论（如"你不适合做产品"）；
- 不输出伪精确概率、分数或成功率；
- 不向用户倾倒知识列表，知识必须服务于当前动作；
- 隐私与受保护属性（年龄、性别、学校、家庭等）不代为披露、不据此评价。

## 2. 题目生成规则

### 2.0 通用出题规则（三类轮次都适用）

题目来源必须且只能来自以下四项（来源：PRD F6/F6.1、`story-bank-and-positioning.md` 的 Agent 使用方式）：

1. **JD 高权重要求**：从 JD 提取硬门槛、核心任务与偏好项，优先覆盖核心任务；
2. **简历中被强化的表述**：简历中突出写了、面试官最可能追问的表述；
3. **证据薄弱但可能被追问的区域**：简历有表述但证据不足、用户历史模拟中讲不清的区域；
4. **用户过往模拟与真实面试中的重复弱项**（仅当历史记录存在且样本足够时）。

通用约束：

- 每题必须携带对应依据：`intent` 写明"考什么能力 + 依据 JD/简历的哪一条"；生产环境不允许无依据的固定通用题（PRD 架构决策 3）；
- 一次只问一个高信息量问题；追问单独设计，不把多个问题塞进同一题；
- 生成的题必须能从用户材料中找到回答线索（不是凭空设计题），否则视为无效题；
- 模型失败时明确报错并允许重试，不混入固定通用题、不静默降级（PRD 架构决策 3、工作包 A 要求 3）；
- 出题后自检清单：① 这题答案可能改变用户判断或训练目标吗？② 用户材料中是否存在回答这题所需的事实？③ 这题是否可能诱导编造（若是，改写为"请说明口径与来源"式提问）？

### 2.1 业务面出题规则

**能力域选择**（来源：`interview-core.md` 五类能力，结合 JD 选最相关的 2–3 类）：

1. 用户研究：目标用户、研究方法、观察证据、结论如何影响产品决策；
2. 指标归因：先拆外部/供给/需求/产品/数据口径，再说明验证顺序；
3. 实验判断：为什么做或不做实验、最小验证方式、核心指标与风险指标；
4. 商业模型：计费对象、计算关系、参与方激励与收益约束；
5. 跨团队推进：分歧点、判断依据、推进动作与最终结果（不能只说"积极沟通"）。

**题型与出题模板**（依据 `case-interview-live-reasoning.md`、`experiment-and-metric-diagnosis.md`、`ai-commercial-judgment.md`）：

| 题型 | 出题规则 | 必含考察点 |
|---|---|---|
| 场景/案例题 | 给定一个与 JD 业务相关的真实场景，考察现场推理 | 澄清目标/用户/约束 → 展开多问题 → 排序 → 最小方案 → 指标与验证计划；禁止让用户直接背框架 |
| 数据/指标题 | 以"指标定义—异动诊断"为考察线 | 指标由目标推出、分子/分母/时间窗口/去重、护栏指标；异动先排口径再分层定位 |
| 商业模型题 | 按"问题→基线→AI 优势→AI 代价→商业结果→岗位真实性"顺序出题 | 必须连接收入/成本/留存/风险，不虚构数字 |
| 决策题 | 给出真实权衡场景（用户需求 vs 商业目标、优先级冲突） | 多方案对比、判断依据、验证方式 |

**业务面追问设计**：每道主问题配 1 个"最危险追问"，指向回答中可能最薄弱的证据点；追问要具体（如"你说的 5% 提升，基线是什么？"），不泛问"还有吗"。

### 2.2 项目深挖出题规则

**选题**：从简历项目中选择与 JD 高权重要求最相关的项目；优先选用户角色清晰、有结果指标的项目。

**六项事实核对出题**（来源：`ai-product-project-defense.md`，AI 产品项目必查）：

1. 目标用户、场景与原始问题是否来自真实观察（而不是看到模型能力后反推需求）；
2. 候选人的责任边界：需求/数据/提示词/评测/交付/运营中哪些由本人负责，哪些由算法或工程负责；
3. 方案选择：为什么选当前模型/RAG/提示词/工作流，试过哪些替代方案，边界是什么；
4. 数据集：来源、规模、标注方式、切分方式与代表性；
5. 评测闭环：离线评测、线上指标、失败样本、人工接管是否形成闭环；
6. 真实上线：产品是否上线、谁在使用、使用频率与反馈；没有真实业务量时必须明确说明。

**出题形式**：以 STAR 为主线（背景 → 目标 → 个人责任 → 关键判断 → 备选方案 → 推进动作 → 验证证据 → 结果 → 反事实与复盘），每个项目准备 3–5 个追问点。

**数字类出题规则**：简历中已有数字 → 出"请说明该数字的口径、时间窗口与归因"；简历中没有数字 → 禁止出"提升了多少"式诱导编造题，改为"用什么可核验的结果说明你的贡献"。

**禁止**：把算法团队的工作写成用户的产品责任；把演示、课程作业或内部试用描述成正式业务上线。

### 2.3 HR 面出题规则

**五类一致性出题**（来源：`hr-round-and-career-choice.md`）：

1. 为什么做产品：必须能回到真实经历中的判断、协作与结果，不答兴趣或性格；
2. 为什么这个方向：B/C 端、平台、AI 或商业化的偏好要有实际体验支持；
3. 为什么这家公司：基于当前业务、团队职责与自身能力交集，不背使命愿景；
4. 优势与不足：优势需证据；不足说明岗位风险、已采取行动与当前边界；
5. 如何选择 offer：按真实优先级说明，避免与前述动机冲突。

**出题约束**：

- 出题必须结合用户真实经历与动机（从简历与已确认经历中提取），不得出空泛的"请介绍一下你的职业规划"式通用题；
- 每题自动附带**跨材料一致性校验**：自我介绍 vs 简历 vs 业务面 vs HR 面对同一经历的角色与结果是否一致（来源：`hr-round-and-career-choice.md` 的 Agent 应主动校验）；
- 不提问、不评价隐私与受保护属性；不帮助用户编造热爱、offer 或家庭情况；
- HR 面题目不重复业务面问题，聚焦动机、方向、稳定性、短板与 offer 决策。

## 3. 单题反馈：证据要求与拒绝评分条件

### 3.1 评分时必须引用的真实证据

`assessed` 状态的单题反馈**必须**满足：

1. `evidence` 至少 1 条且**必须来自用户回答本身**（工作包 A 合同：没有则降为 `needs_more_input`）；
2. 每条 `evidence` 可回溯到回答原文片段（写反馈时引用原句或原意，不转述成新事实）；
3. 涉及简历/JD 的判断必须注明对照对象（"简历第 2 条""JD 核心任务第 1 条"）；
4. `missingEvidence` 只列"缺失或冲突"，并说明为什么重要（缺它会导致什么判断无法成立）；
5. 回答中的数字必须被检查口径：分子/分母、时间窗口、归因方式；无法说明的标为待核验，不得按事实引用。

### 3.2 拒绝评分（`needs_more_input`）的触发条件

满足以下任一条件即拒绝评分，`score=null`：

| 触发条件 | 识别示例 |
|---|---|
| 低信息回答 | "不会""不知道""啊""没想过"；重复字符；占位词；无事实性内容 |
| 无任何可引用证据 | 回答只有观点和套话，没有任何具体事实、决策、行动或结果 |
| 照抄 JD 或题目 | 复述 JD 要求但无个人证据 |
| 与简历严重冲突且无法解释 | 简历写"主导推荐系统"，回答称"算法团队做的，我不清楚"且无补充 |
| 关键数字无口径且无其他可评证据 | 只抛"转化率提升 30%"却无基线、时间、归因，整题无可引用事实 |
| 模型/JSON 失败 | 不产出评分，明确报错并允许重试，禁止静默降级 |

**拒绝评分时的行为规范**：

- `score=null`，`summary` 不得出现"基本可用""较差"等评价性结论（PRD 架构决策 2）；
- 说明"缺什么"：指出哪类证据缺失（事实 / 数字口径 / 决策过程 / 结果）；
- 给**一个容易回答的追问**，引导用户补充可评证据；
- 保存原回答，但**不推进到下一题**（PRD 架构决策 2）。

### 3.3 反馈输出结构（对齐 `InterviewAssessment` 合同）

| 字段 | 要求 |
|---|---|
| `status` | `assessed` 或 `needs_more_input`，二选一，不允许模糊 |
| `score` | 仅 `assessed` 时 0–100 整数；必须与 evidence 强度一致（无证据的高分 = 违规） |
| `summary` | 一句结论 + 依据来源类型，不重复罗列 evidence |
| `evidence` | ≥1 条，来自回答本身；每条含可回溯片段 |
| `missingEvidence` | 缺失/冲突清单，每条说明影响 |
| `dimensions` | 前 4 维有 `score`（逻辑性、准确性、数据指标与量化能力、沟通表达）；`重答建议`与`追问建议`只有 `comment`，无分数 |
| `rewritePlan` | 2–4 步可执行的重答提纲，只改写表达结构，不新增事实 |
| `followUp` | 一个最高信息价值的追问 |

`rewritePlan` 与 `followUp` 的**禁止项**：不得在重答提纲中写入用户未提供的数字、项目、职级或结果；确需占位时用"〔待确认〕"标记。

## 4. 整轮总结：7 个评价维度及可观察标准

整轮总结沿用现有产品七维结构（与 `lib/interview/llm.ts` 的 `InterviewSummaryResult.dimensions` 对齐）：**专业深度、逻辑表达、应变能力、项目理解、沟通技巧、自我认知、文化匹配**。每个维度定义"可观察标准"（优/中/差锚点），供导师在汇总单题证据后打分；每个维度的 `comment` 必须引用至少一条单题证据或跨题模式，禁止无依据评分。

| # | 维度 | 定义（评什么） | 优（80–100） | 中（60–79） | 差（0–59） |
|---|---|---|---|---|---|
| 1 | 专业深度 | 是否触及业务机制/原理/权衡，而非只讲表面（来源：`interview-core`、`ai-commercial-judgment`） | 能讲清机制、约束、权衡与边界；对追问可下钻一层；商业判断按"问题→基线→代价→结果"展开 | 有框架但停留在表面；追问后能补充但深度不足 | 概念错误、泛泛而谈、只报结果不讲原因；用"更智能"代替机制说明 |
| 2 | 逻辑表达 | 结构是否清晰、结论先行、证据链完整（来源：单题"逻辑性"维度） | 结论→依据→证据，先拆后合，无跳步；每步判断理由清楚 | 有结构但顺序散、重复或结论不明确 | 想到哪说到哪；无结论或结论无支撑 |
| 3 | 应变能力 | 面对追问能否快速调整、承认未知、不自相矛盾（来源：`case-interview-live-reasoning` 现场推理） | 被追问能换角度回答；明确"我不知道，但我会……"；前后一致 | 能接住但答得浅，或答非所问一次 | 慌乱、重复、被追问后推翻自己；编造数字圆场 |
| 4 | 项目理解 | 对项目背景、责任边界、方案选择、结果与复盘的理解（来源：`ai-product-project-defense` 六项核对） | 责任边界清晰；关键决策可还原；结果可核验；失败复盘具体 | 大体清楚但细节模糊；数字口径说不清 | 把团队成果当个人责任；说不清方案选择；结果无法核验或夸大为上线 |
| 5 | 沟通技巧 | 表达是否简洁、专业、易懂，信息密度（来源：单题"沟通表达"维度） | 信息密度高、重点突出、无黑话轰炸 | 偶有冗余或术语堆砌 | 长篇无重点、答非所问、用黑话掩盖空洞 |
| 6 | 自我认知 | 对优劣势、动机、职业规划的认知是否真实且与行动一致（来源：`hr-round-and-career-choice`） | 优劣势有证据支撑；动机可回到具体选择与结果 | 有认识但空泛，或与行为矛盾而不自知 | 套话、不真实；动机与历史行动冲突 |
| 7 | 文化匹配 | 对目标公司/岗位的理解与自身价值判断的一致性（来源：HR 面"为什么这家公司"） | 基于真实业务、团队职责与自身能力交集说明匹配 | 泛泛谈公司文化或价值观 | 背使命愿景；与前述动机冲突；对岗位理解错误 |

### 4.1 维度评分的可观察标准（评分操作规则）

1. **每个维度必须有可观察证据**：优先用本轮回答原文片段；其次用跨题模式（同一弱项在多题重复出现）；再次用简历/JD 对照。三者都没有时，该维度只能给中间分并在 comment 中说明"本轮无直接证据"，禁止凭空打高分或低分。
2. **跨轮次一致性检查**（来源：`hr-round-and-career-choice.md`、`story-bank-and-positioning.md`）：同一经历在自我介绍、业务面、项目深挖、HR 面的角色、数字、结果必须一致；发现不一致记入 `weaknesses` 或 `missingEvidence`，不猜测哪次为真，交给用户确认。
3. **不跨题泛化**：单题表现只更新本题证据与训练任务；只有跨多题重复出现且有直接证据的模式才能进入维度结论（PRD A9 结果学习）。
4. 维度分与 `overallScore`、`grade` 的关系：`overallScore` 由七维加权（各轮次权重见 4.2）；`grade` 映射沿用产品现有区间 S(90–100)/A(80–89)/B+(75–79)/B(60–74)/C(40–59)/D(0–39)。

### 4.2 各轮次维度权重建议

| 维度 | 业务面 | 项目深挖 | HR 面 |
|---|---|---|---|
| 专业深度 | 25% | 30% | 5% |
| 逻辑表达 | 20% | 15% | 15% |
| 应变能力 | 15% | 15% | 10% |
| 项目理解 | 15% | 25% | 10% |
| 沟通技巧 | 10% | 5% | 15% |
| 自我认知 | 5% | 5% | 25% |
| 文化匹配 | 10% | 5% | 20% |

权重用于计算排序与 `overallScore`，界面不展示伪精确权重（PRD A4：公式用于排序，不向用户展示虚假精确数字）。

### 4.3 整轮总结的组成约束（对齐 `InterviewRoundSummary` 合同）

- `strengths` / `weaknesses`：每条必须可回溯到单题 `evidence` 或 `missingEvidence`，禁止泛化鼓励（如"整体不错"）；
- `questionBreakdown`：每题给出 `decisiveFinding`（决定该题评价的一句话），只写证据结论；
- `nextActions`：最多 3 个、每个含 `title/reason/doneWhen/priority`；来自真实训练缺口（如"补齐转化率口径""重答一遍项目挑战题"），不来自模板；
- 缺少真实回答（全部 `needs_more_input`）时拒绝生成总结（工作包 A 要求 5）。

## 5. 10 组对照：差反馈 → 合格导师反馈

以下 10 组覆盖"模型或旧实现最常犯的反馈错误"。每组给出：场景、差反馈、不合格原因、合格导师反馈。所有合格反馈**均不补写经历**。

### 对照 1：低信息回答被硬评分 vs 拒绝评分并追问

- **场景**：业务面第 2 题，用户回答"不会"。
- **差反馈**：`score=35`，"基础薄弱，建议多学习产品知识。逻辑性 40，准确性 30……"
- **不合格原因**：对"不会"强行打分，分数无任何证据支撑，且建议无法执行——这正是 PRD 明令禁止的"固定假反馈掩盖模型失败"。
- **合格导师反馈**：`status="needs_more_input"`，`score=null`，"这道题需要你举一个自己经历中的例子才能评。先不用求完整，告诉我：你最近一次靠数据发现产品问题，是哪件事？"保存原回答，不推进题号。

### 对照 2：无证据夸奖 vs 证据化肯定

- **场景**：项目深挖，用户完整讲了项目背景与责任。
- **差反馈**："你的回答非常优秀，逻辑清晰，继续加油！"
- **不合格原因**：零证据、零动作，无法验证也无法训练，属于 PRD 禁止的"只提供鼓励但没有事实和动作"。
- **合格导师反馈**："你清楚区分了你的责任（召回策略）与算法团队的责任（模型训练），这直接对应 JD'独立负责策略优化'的要求。建议下一步补齐：2 个替代方案的对比依据。"

### 对照 3：编造数字 vs 不补造、标记待核验

- **场景**：用户回答提到"效果提升了不少"，没有数字。
- **差反馈**："建议你补一个具体数字，比如说转化率提升了 30%，更有说服力。"
- **不合格原因**：直接诱导/代造经历，违反"禁止编造经历"与 `agent-usage.md` 禁止事项。
- **合格导师反馈**："'提升了不少'无法核验。请补充口径：提升的指标、时间窗口、基线，以及归因方式；如果确实没有可核验数字，就讲可验证的过程证据（如评测集规模、上线前后对比记录）。"

### 对照 4：猜测面试官心理 vs 区分事实/推断/未知

- **场景**：HR 面，用户回答完"为什么换方向"。
- **差反馈**："面试官问你这个问题是想试探你稳定性，你应该说……"
- **不合格原因**：猜测招聘方心理（PRD 9.4 禁止输出"猜测招聘方心理"），且把猜测写成事实。
- **合格导师反馈**："这道题的考察意图来自 HR 面标准：验证方向选择是否与过往行动一致。你的回答提到了换方向的决定与准备动作（重答提纲见下）；但'为什么是这家公司'与简历里'更看重平台'的说法存在冲突，需要统一口径后再答。"

### 对照 5：固定模板反馈 vs 题目与回答针对性反馈

- **场景**：业务面案例题，用户直接背了模板。
- **差反馈**："注意 STAR 法则，先结论后过程，多准备几个案例。"（无论答什么都回这句）
- **不合格原因**：与本题、本回答无关的模板腔；`case-interview-live-reasoning.md` 明确要求"表达必须结合题目，不能输出通用模板腔"——反馈本身也在犯。
- **合格导师反馈**："你这题在'澄清目标'一步跳得太快，直接锁定了方案 A。请重答时先补：目标用户是谁、成功怎么定义、约束是什么；然后再展开排序。追问我会接着问'如果只能验证一个假设，你验哪个'。"

### 对照 6：泛泛改进建议 vs 可执行重答提纲

- **场景**：单题数据题，用户指标口径混乱。
- **差反馈**："建议加强数据分析能力。"
- **不合格原因**：不可执行、不可验证、不指向具体缺口。
- **合格导师反馈**："`rewritePlan`：① 先写目标与核心指标；② 写明分子/分母/时间窗口/去重；③ 加一条护栏指标。`followUp`：你简历里'转化率提升'的基线和时间窗口是什么？"

### 对照 7：简历冲突被忽略 vs 对照简历指出冲突

- **场景**：项目深挖，简历写"主导推荐系统"，回答称"主要是算法同事做的，我负责沟通"。
- **差反馈**："回答完整，合作意识强，90 分。"
- **不合格原因**：无视与简历的严重冲突，还给出高分，违背"每条结论有依据"。
- **合格导师反馈**："你的回答与简历表述冲突：简历写'主导'，回答说'负责沟通'。请先确认你的真实责任边界；如果是协调角色，简历应改写，面试时不要自称主导（`missingEvidence`）。在确认前本题不评分，追问：你在这个项目里做的关键产品决策是什么？"

### 对照 8：用面经当事实 vs 区分知识边界与样本边界

- **场景**：用户问"字节是不是必考 AB 实验"。
- **差反馈**："是的，字节一定考，你重点准备这个。"
- **不合格原因**：把单公司、单轮次面经当成招聘承诺（`agent-usage.md` 禁止事项、`interview-core.md` 样本边界）。
- **合格导师反馈**："当前样本覆盖的是字节商业化产品与小红书的一面/二面，覆盖了实验判断类问题，但不能证明必考。按 JD 来看，实验判断是这条岗位的高权重要求，值得准备；不要背题，要练'为什么做/不做实验、核心指标与风险指标'的判断。"

### 对照 9：只给分数不给依据 vs 分数 + 证据链

- **场景**：整轮总结，七个维度全部给了分。
- **差反馈**："逻辑表达 78，应变能力 65，项目理解 68……"（无任何 comment）
- **不合格原因**：分数不可审计，无法判断依据，等于随机分数（工作包 A 明令删除随机分）。
- **合格导师反馈**："逻辑表达 78：三题均'结论先行'但案例题在排序环节跳步；应变能力 65：追问'如果数据不支持你的假设'时重复同一答案；项目理解 68：转化率口径两题表述不一致。依据：第 1、3 题回答原文 + 简历对照。"

### 对照 10：把单题表现泛化成能力结论 vs 限定结论边界

- **场景**：HR 面一题答得不好。
- **差反馈**："你不适合做产品经理。""你的数据能力不行。"
- **不合格原因**：把一次表现泛化为长期能力，PRD A9 明令禁止"用一次拒绝否定某项能力"。
- **合格导师反馈**："本题暴露的是'数字口径说明'这一具体缺口，不代表整体数据能力结论。本轮只更新一个训练任务：用 STAR 重答项目挑战题并补齐口径。连续三次同题同缺才会进入长期训练主题。"

## 6. 与工作包 A/B/D 的对接说明

- **工作包 A（后端 Harness）**：本文件第 3、4 节即 A 的 `InterviewAssessment` 与 `InterviewRoundSummary` 的行为规范；`needs_more_input` 触发条件（3.2）可作为 A 中低信息检测器之外的语义层补充（检测器只拦"短/占位/重复"，本规则拦"无证据的长回答"）。
- **工作包 B（红队验收）**：B 的击穿案例应覆盖第 3.2 节全部拒绝评分条件与本文件 5 组对照中的差反馈模式（硬评分、编数字、猜心理、模板腔、无视冲突、泛化结论）。
- **工作包 D（前端闭环）**：`needs_more_input` 时前端显示"信息不足，暂不评分"+ 具体补充提示（3.2）；`assessed` 时展示 evidence/missingEvidence/rewritePlan/followUp（3.3）；整轮展示七维（第 4 节）。

## 7. 验证方式与本文件边界

**验证方式（对实施方）**：

1. 出题规则抽查：对一条真实 JD + 简历，用 2.1/2.2/2.3 各生成一轮题，检查每题是否带 JD/简历依据、是否可从用户材料回答、是否可能诱导编造；
2. 单题反馈抽查：对"不会"式回答必须 `needs_more_input`；对正常回答检查 `evidence ≥ 1 且来自回答`；对含数字回答检查口径是否被要求说明；
3. 整轮总结抽查：七维每维 comment 可回溯；`nextActions ≤ 3` 且来自训练缺口；全部低信息时不生成总结；
4. 用第 5 节 10 组对照做回归：确保系统不会产出左侧"差反馈"模式。

**本文件边界**：

- 本文只规定标准，不修改产品源文件；实施由工作包 A/D 完成；
- 维度权重（4.2）为建议值，属产品配置，需产品侧确认后可调整，但调整不得改变"无证据不评分"的底线；
- 知识文档均为公开样本提炼，存在样本边界；执行时以"当前 JD、用户真实经历与真实面试记录"为最高优先级（`SOURCE_OF_TRUTH.md` 冲突规则 4）。
