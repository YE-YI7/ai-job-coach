## #1 · Offer 对比计算器

### 定位与关键词
- 主词：`offer 对比计算器`
- 长尾变体（各写成一处小标题/FAQ，覆盖真实问法）：
  - `两个 offer 选哪个`
  - `总包 / 年包 怎么算`
  - `月薪换算年包 公式`
  - `跳槽 首年 到手 差多少`
  - `五险一金基数 对 税后 的影响`
  - `期权 / 签字费 / 公积金 怎么并进总包`
- 搜索意图：手里有 1–3 个 offer（或在看跳槽机会），想**把不同薪酬结构换算成可比口径**（税后到手、时薪、首年净得），怕只看月薪被坑。付费意图强：谈薪 / offer 决策是成熟付费场景。
- 竞争事实：已有通用薪酬计算器（masmo、道积君、太卷了 CashCalc 等），但都停在"纯薪酬换算"，没有"放进你的求职过程里、连同岗位成长/条款/风险一起比"。这就是我们的差异点。

### Title / meta / H1
- Title：`Offer 对比计算器：总包·税后到手·时薪 一次性算清（2026）`
- Meta description：`贴进 2–3 个 offer 的月薪、年终奖、公积金基数、签字费、期权，实时算出年包、税后到手、时薪和跳槽首年净差额。数字均为估算，结果可存进你的求职作战盘一起比成长与风险。`
- H1：`别只比月薪。把每个 offer 换成"税后到手 + 时薪 + 首年净得"再决定。`

### 首屏（above the fold）
- 左/上：一句 H1 + 三行"我们比什么"（年包 / 税后到手 / 时薪+首年净差）。
- 右/主：**工具卡直接可见可填**，不放长介绍。输入即出结果，无需登录；导出/保存才引导注册或转免费 Agent。
- 主 CTA（工具内）：`算出对比`。次级：`添加第 3 个 offer`。

### 工具主体
输入（每个 offer 一列，最多 3 列）：
- 月薪、发放月数（12/13/14/…）、年终奖（个月或固定额）
- 五险一金缴纳基数、公积金比例、补充公积金
- 签字费、股票/期权（授予额 + 归属年限，按年化摊销，标注"按你的假设线性，未考虑税与折现"）
- 工作时长假设（每周小时、是否大小周、通勤），用于算**时薪**
- 城市（用于社保/公积金上下限与个税专项附加的默认区间，标注为粗略口径）

计算/检测过程（先展示，再给结论——遵循"先证据后结论"）：
1. 年包 = 月薪×发放月数 + 年终奖 + 签字费首年部分 + 期权年化（各自列出）
2. 税后到手（月度/年度）：扣五险一金个人部分 + 个税（用**明示的粗略税率/速算表**，页面注明"不含专项附加扣除的具体项，实际以申报为准"）
3. 时薪 = 年税后到手 ÷（每周小时×52×在职月占比）
4. 跳槽首年净差额 = 新 offer 首年实际到手 − 现 offer 同期（考虑签字费、期权未归属、公积金账户留存）
5. 输出：**三张对比表 + 一张"差异主要来自哪几项"的归因**（例：A 与 B 差 9 万，主要由公积金基数 + 签字费贡献）

结果下方结论区：一句话倾向（"若只比到手与成长，B 更稳；A 的期权需满 2 年才体现"）+ 明确写出该结论依赖的假设，允许用户改假设。

### 转场（软引导，不硬挡）
- `把这几份 offer 存进我的求职作战盘，连同岗位职责、直属 leader、晋升节奏一起比 →`（引导注册 / 登录 / 免费 Agent 本地版）
- 已登录用户：一键生成一条 `谈薪与 Offer` 记录，后续可请导师帮拟还价话术。

### 支撑内容（工具下方，短，服务 SEO 与转化）
- `总包/年包到底怎么算` 3–5 行（含公式）
- `只看月薪为什么容易被坑`（公积金、基数、期权未归属、大小周稀释时薪）
- `谈薪时可以直接问 HR 的 5 个问题`（清单）

### FAQ（覆盖长尾问法 + 建议加 `FAQPage` 结构化数据）
1. 两个 offer 总包一样要不要选更高的？→ 引到公积金基数、期权兑现、团队与晋升。
2. 签字费要不要算进总包？→ 算首年但注明非持续。
3. 期权怎么并进年包？→ 线性年化 + 未税未折现的假设说明。
4. 大小周怎么影响时薪？→ 用实际周工时算。
5. 五险一金按最低基数交会差多少？→ 用计算器现场演示。

### 技术/埋点/内链
- slug：`/tools/offer-compare`（静态化、秒开、可被索引）
- 内链：→ `#2 JD↔简历缺口`、→ 产品主页 `/cockpit`、→ 谈薪 tab 说明页
- 埋点（接现有 `lib/product-events`）：`offer_calc_used`、`offer_added`、`offer_save_click`、`offer_save_signup`。用来测"工具→注册"真实转化。
- 交付依赖：**这是一个需要新建的公开免费计算器**（当前产品里没有可直接对外的独立计算页）。工程量≈前端表单 + 纯函数计算模块 + 单测；无鉴权、无模型调用，成本低。

## #2 · JD ↔ 简历缺口检测

### 定位与关键词
- 主词：`简历 JD 匹配度检测`
- 长尾变体：
  - `投不同岗位 简历要不要改`
  - `简历 缺 哪些 关键词`
  - `ATS 机筛 为什么挂`
  - `简历 和 JD 对不上 怎么办`
  - `怎么针对一个岗位改简历`
- 搜索意图：手上有一份简历 + 一个具体 JD，想知道**这份简历投这个岗位缺什么、会不会被机器刷掉、具体该补哪几处**。付费意图强（简历优化/改简历是成熟付费类目）。
- 竞争事实：头部 `ATS简历` 拥挤（Resume-Matcher、超级简历、Reactive Resume 等，且知乎热帖多）。我们**不硬打"打分/ATS 检测"头部词**，切"缺口对照 + 一岗一版"这条更贴益职、通用 checker 复制不了的角度：不只给分，而是说清"缺哪条经历/关键词、这句话有没有事实支撑"。

### Title / meta / H1
- Title：`简历对不上 JD？逐条找出缺的关键词和没被证明的经历（附改法）`
- Meta description：`贴进你的简历和目标 JD，逐条列出：JD 要求里你没写的关键词、写了但缺少证据/结果的经历、以及这个岗位最可能被追问的点。不编造经历，缺的就标待确认。`
- H1：`不是"改得更花"，是补上 JD 要、你简历缺的那几条。`

### 首屏
- H1 + 一句"我们做的是缺口对照，不是打分"。
- 工具：两个输入框（粘贴简历 / 粘贴 JD，或上传 `.pdf/.docx`）+ 主 CTA `找出缺口`。
- 隐私条：`材料默认本地处理，未经你确认不会上传云端；不会替你编经历。`（对齐产品隐私承诺，很关键）

### 工具主体（复用后端已有能力，别新造模型链）
输入后走**现有教练/grounding 管线**（`/api/coach/resume-review`、`/api/coach/agent` 的 resume-grounding 与 evidence 逻辑、`lib/coach-harness/material-gap`），输出遵循"先证据后结论"：
1. **JD 要求清单**：拆出硬门槛（如"5 年经验""某技术栈"）与加分项，各自标注 JD 原文依据。
2. **关键词/要求缺口**：JD 出现但简历未命中的，逐条列出（区分"真没有 vs 有但没写"）。
3. **证据强度**：简历里写了但缺结果/时间/职责边界的句子，标"未被证明"，**不得**被系统当成"已确认经历"（呼应我们已修的 P0 事实可靠性）。
4. **最可能被追问的 3 点**：直接连到模拟面试。
5. 结论：一句话"这份投这个岗位，主要卡在 X / 缺 Y"，附"要不要我基于缺口出一版针对该岗位的简历？"

### 转场
- `一键生成一岗一版简历草稿（缺的先留占位，等你补）` → 引导进 `/cockpit` 简历工作室 或 免费 Agent 本地版
- `把这份缺口清单存进作战盘，跟进这个岗位` → 注册/登录

### 支撑内容
- `投不同岗位到底要不要各改一版简历`（给判断，不是一刀切）
- `ATS 机筛挂在哪：格式？关键词？还是经历没量化`
- `缺的经历不能编——可以怎么真实地补`（呼应品牌"不虚构"）

### FAQ
1. ATS 打分 0–100 准吗？→ 别信伪精确分，看具体缺哪条。
2. 没做过的能写上去吗？→ 不能，标为待确认/用相关证据替代。
3. 改简历要改关键词堆进去吗？→ 是"命中真实经历对应的关键词"，不是堆词。
4. 一份简历投多个岗位行不行？→ 分岗位差异大时按缺口各出一版。

### 技术/埋点/内链
- slug：`/tools/resume-jd-gap`
- 内链：→ `#1 Offer 对比计算器`、→ 简历工作室、→ 模拟面试（缺口最可能被追问点直连）
- 埋点：`resume_gap_used`、`resume_gap_missing`（缺哪类）、`resume_gap_to_version_click`、`resume_gap_signup`
- 交付依赖：**大量复用已有后端**（简历解析、evidence/grounding、material-gap、一岗一简历草稿），主要新增是一个可对外、无需登录即可跑一遍的公开壳 + 结果呈现，成本比 #1 略高（涉及模型调用与额度），需要给公开页做防滥用/限额。

## 两页共用的骨架与规范（写手/前端照此）
1. 结构顺序：命中意图的 Title/H1 → **首屏可用工具** → 先证据后结论的结果 → 软引导转 cockpit/注册 → 短支撑内容 → FAQ（+ `FAQPage` schema）→ 内链。
2. 每页都要能**独立交付价值**（不注册也能拿到结果/清单），转注册只做锦上添花的"保存/一键生成"。
3. 数字/匹配度一律标"估算·以实际为准"，**不出现**通过率/保录取/伪精确分。
4. 移动优先、键盘可用、状态不只靠颜色、`prefers-reduced-motion`（对齐无障碍要求）。
5. 措辞去 AI 味、带"人味儿"、别像冷冰冰的 SaaS；也不夸大。
6. 先上这两页跑 2 周小流量，用上面的埋点看 `工具使用 → 保存 → 注册` 漏斗，验证"通用对话替代不了"再决定要不要铺 #3–#6。
