# 简历 Agent：段落编辑、整稿检查与逐问补充

2026-10-19 · 产品设计讨论稿。用户本轮提出职责边界和成本问题；本文是建议契约与验收设计，不代表新 Agent、后台反馈入口或返修机制已经实现/上线。未经本轮定案，不更改正式编排，不运行收费模型做架构实验。

## 产品目标与当前证据

目标是把用户已有事实变成一份重点清楚、可读、可信、适合当前申请场景的简历；不是凑修改次数、统一模板或把内部规则分拉到100。保留现有左侧栏、旧作答、用户已采纳/拒绝决定和积分，缺信息不阻断能安全完成的修改。

证据：正式 Eval 运行 `9d94e3ea-3b07-4ced-b635-ac68a3038b96`，对应内部简历 Trace `42f131d8-92b6-448f-a3a7-5ce0f95f8798`，40,947ms；改稿 Agent span 17,941ms、独立质检 Agent span 10,806ms，同为 deepseek-v4-flash。六处修改起草时都丢失原加粗领句，独立质检仍全部 useful/passed。当前80为规则分，非LLM自评。这里只是一个真实请求，不是p50/p95或并行对照结果。

补查 `ai_generation_events`，先按该正式记录的本人账号/时间窗限定，再以内部Trace的requestHash与遥测requestId的SHA256精确核对成功：起草输入10,528 / 输出1,342、review输入11,529 / 输出517；两次合计输入22,057 / 输出1,859，总23,916 tokens，缓存命中均0、重试均0。模型调用遥测latency分别14,064/7,152ms，与包含更大调用边界的span不是同一口径，不相加或混替，未对差额做逐项归因。金额估算与pricing_version均null，没有渠道实际结算账单，不能将源码内另一路估价函数的费率冒充本次扣费。

## 什么叫“好简历”

事实正确是硬门槛；其余维度按场景评审，允许不适用。初期先保留逐项判断、证据、原因和缺口，不用未经校准的总分决定交付或无穷追问。100分只作改进愿景，不要求每段都有数字、STAR四要素或领导角色。

| 维度 | 可观察的通过依据 | 不能当作通过 |
| --- | --- | --- |
| 事实与责任 | 每个重要主张回指本人材料；公司、时间、职称、数字、参与程度、提案/原型/上线状态正确 | 来自网络/优秀案例的数字；模型自行补出来的漂亮结果 |
| 定位与取舍 | 有JD时，最相关的真实证据容易找到；无JD时不猜岗位，优先改善现稿，方向不明才问 | 机械塞满JD词、整份都像另一个岗位、删掉真实但难量化的贡献 |
| 段落质量 | 看得懂本人做了什么、对象是什么、交付/已知结果或用途是什么；亮点具体，面试可追问 | 空泛能力标签、术语堆砌、只有想法却写成成果、每段强求量化 |
| 整稿质量 | 重点靠前、篇幅合理、少重复，跨经历责任/时间不矛盾，信息密度平衡 | 六条单看不错就直接宣布整份可投；反复强调同一卖点 |
| 风格与结构 | 原稿已认可的标题层级、要点领句、列表、日期和语气得到继承；有理由才改 | 自动换整份模板；删空话时顺便抹掉整份加粗领句结构 |
| 交付可用性 | 保存/刷新/导出分别有证据，实际PDF无裁切/乱码/错序、内容与所选版本一致 | Markdown检查替代PDF目视/文字层验收；成功保存即认定简历质量合格 |

量化信息是强证据的一种，而非必需装饰。用户能提供范围、频次、周期、交付用途或真实规模时可以使用；不能诱导猜效果。所谓“钩子”是能解释判断/方法/取舍/结果的真实细节，不是故意卖关子或添加面试官想看的虚构亮点。

## 推荐默认链路

```text
本人材料 + JD（可无） + 相关写法知识/必要公开调查
                 ↓
程序构建有来源的事实/编辑简报（默认不新增LLM整合）
       ├─ 段落缺口 → 导师一次问一个 → 新的本人事实版本 ─┐
       └─ 编辑Agent按段落边界改稿 ←─────────────────────┘
                 ↓
程序检查引用、修改范围/冲突，并组装当前整稿候选
                 ↓
独立整稿检查Agent（只诊断，不输出替换正文）
       ├─ 具体可改问题 → 返还原编辑Agent → 有界返修 → 复查
       ├─ 确缺本人事实 → 导师队列；其他安全修改继续交付
       └─ 通过 → 该版本完成内容检查；另验保存、刷新、实际PDF
```

### 简报：保留来源，不把调查结果压成没有出处的结论

简报至少包含：traceId、材料版本/hash、可选JD版本、事实台账及sourceId、每段的允许修改范围、已采纳/拒绝决定、原稿风格契约、相关知识documentId/版本/适用范围、公开调查原URL与时间和冲突标记、尚缺信息。三类信息分开：本人事实、岗位公开要求、可参考写法。网络与知识库不是本人经历来源。

默认复用已有检索/事实结构由程序选取去重，不让所有编辑者各自重新搜索。只有多份资料存在真实冲突、材料长到直接使用明显浪费、或任务需要复杂取舍时，才候选调用整合Agent；整合不能删除出处/分歧，且必须用对照实验证明有价值。公开检索不含姓名、电话、邮箱或整份私有简历；外部网页内容按不可信材料处理。

### 编辑Agent：按段落负责，读到必要全局约束

负责自己这段的事实表达、动作/交付、信息取舍、亮点、空话与术语。输入给该段原文/相邻标题、相关事实/写法、只读的整稿定位摘要和styleContract；“只专注这一段”不等于把整稿风格完全藏起来。输出taskId、sectionId、beforeHash、before/after、来源与修改理由、可选具体缺口。不得改其他段落/联系方式、移植外部数字、覆盖用户手工编辑或反复复活已拒绝意见。

先改能改的；真没有编辑价值就保留原文，不要求每段都必须产生diff。有加粗要点领句的稿，旧领句空泛时重写为具体领句，不机械保留坏文字，也不强迫所有原本没有领句的简历新增领句。

### 整稿检查Agent：检查是不是好简历，也检查格式

读取应用修改后的完整候选，不只看零散changes；同时提供必要原文/事实索引、JD、styleContract和用户决定。复核事实与责任边界，重点看逐段难发现的定位/排序、重复、跨段矛盾、篇幅与重点平衡、语气/领句/层级一致性。程序先做可确定的引用、范围、占位符/Markdown与版本冲突检查；LLM不替代实际PDF几何检查。

输出仅允许：候选hash、pass/revise/needs_information/partial、逐项评估及可定位的findings。每条问题有findingId、sectionId/changeId、问题维度、严重度、原句或对照证据、期望约束、ownerTaskId、是缺信息还是编辑错误。禁止输出after/完整重写稿，也不能一面指出必改问题一面宣告已通过。

发现表达/结构错误回原编辑者；发现缺事实送导师；发现渲染/PDF缺陷归交付检查，不让文字编辑者靠删事实掩盖CSS问题。独立是职责与评估维度独立，不保证换模型就客观；可先复用同模型，但不要机械复制会诱发同类偏差的起草提示词作为全部审查标准。

### 导师：一个共享缺口队列，不轮流盘问

按“这条答案能否实质改变该段改写”的优先级，一次问一个；与编辑并行但不等待用户才开始改稿。每个缺口有gapId、段落/事实引用、为什么值得问、已问/已答/跳过状态。只做过哪些环节先于夸张效果，记不清/没有/跳过是有效结果。低影响缺项不为凑100分继续追问。

回答仍是本人自述来源，更新材料版本后只重改受影响段落并复查受影响的全局约束。答案不能被当成再次重写整份的理由；回答和编辑同时完成时以版本/hash防过期覆盖。已有安全修改先显示为工作稿，不把尚未检查的稿件显示为“整稿检查通过”。

### 返修预算与终态

建议首版：1次起草 + 1次整稿检查；最多1次自动返修 + 1次复查，不在同一请求内循环追问或无限自评。每次返修保留父Trace、iteration、findingIds、负责编辑task、输入/输出、耗时/token/费用证据。未解决时返回具体未决项及可用版本，不编补缺失事实、不丢已经安全的修改、不强制用户反复支付重来。不用多调用一遍“自评”掩盖原质检缺维度。

## 是否要“先整合，再多个编辑”

以下以3个独立待改段落、无返修为例。是调用结构比较，不是已测加速或人民币报价。检索与导师独立计，三种方案都需同样的信息边界。

| 方案 | 主链LLM调用数 | 关键等待路径 | 判断 |
| --- | --- | --- | --- |
| 程序简报 → 单编辑一次起草、按段返回隔离patch → 整稿检查 | 2 | E + G | 建议默认，避免重复上下文和合并协调 |
| 程序简报 → 同一编辑分3次串行改段 → 整稿检查 | 4 | E1 + E2 + E3 + G | 与下面并行方案才是同调用数的调度对照 |
| 程序简报 → 3段编辑并行 → 整稿检查 | 4 | 理想为max(E1,E2,E3) + 合并 + G | 独立长段可能更快；不代表是单编辑耗时除以3 |
| LLM整合 → 3段编辑并行 → 整稿检查 | 5 | S + max(E1,E2,E3) + 合并 + G | 多一个串行S；默认不启用 |

Agent名称/实例数不是计费单位，实际模型调用才是。默认两次主链调用意味着一次起草按各task的允许范围分别输出patch，不意味着每段各调用一次却只记一次费用。若需要更严格的单段注意力隔离、每段独立调用，就进入N次起草+1次总审；串行与并行调用数相同，主要差异在调度、上下文分配和整体返修，而非凭“多Agent”这个标签省钱。

费用为各调用 `输入token×输入单价 + 输出token×输出单价` 的合计（另按供应商区分缓存命中、推理token、失败/重试）。调用数不是费用倍数，但多编辑重复传事实/知识/全稿通常会增加消耗。仅作条件算例：若三个编辑都复制本次起草的完整上下文，起草输入就从10,528变为31,584 tokens，还没有计总审或新增整合步骤；这是重复上下文假设，不是并行实测或必然成本倍数。按段落裁剪上下文可以改变这笔账，需同时验证来源完整与风格保留。现只有单次真实token基线，没有架构对照/实际扣费账单，不能给“贵2倍/快3倍”或人民币结论；17.9秒的单编辑也不能推算每段独立请求的速度。

预注册对照后再决定：相同材料/事实源/知识版本/styleContract/模型、总token预算和同一独立评估；覆盖普通、已较好、薄材料、无JD、跨岗、格式复杂样本。开发与留出案例分离，记录质量通过、无依据主张、漏改、风格回退、返修次数、问题轮数、端到端p50/p95、输入/输出/缓存token和真实费用。只有质量不退步、延迟改善足够覆盖成本和复杂性时才启用并行；阈值与费用预算待定，未开展收费A/B。

公开参照：[Anthropic 的工作流模式](https://www.anthropic.com/engineering/building-effective-agents)强调可独立切分时才适合并行、生成评估循环需要清晰标准；其[多Agent研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)明确有更高token成本与任务依赖限制。那是研究系统经验，不将其成本倍数或加速成绩套到益职简历。

## 规则放哪里

- 知识库放“好简历的判断依据/公开写法/事实和场景边界”，继续遵守SOURCE_OF_TRUTH与来源审读；本轮不把讨论稿编译成运行知识。
- Skill或版本化Agent契约放输入输出、修改范围、只审不改、返修/停止、并发版本保护和何时向导师发问题；规则需真正注入调用，不能只放一个文件便称已接通。
- 私有Eval案例库放用户反馈、真实Trace/change/span指针、判断依据、预期行为、修复版本与回归状态，不进入公共写法库，不把本人经历作为其他用户素材。

## 每次具体反馈的案例与网站入口契约

每条案例固定caseId，必须有完整traceId、changeId（整稿问题可为空但标明scope=whole_document）、相关stage/spanId、反馈来源、观察到的问题、用户认可部分、期望行为、诊断证据/推断、状态与回归结果。账号归属由服务端用正式Trace的user_id验证，不按姓名/邮箱猜测或由客户端提交ownerId。没有准确Trace时记待关联，不造ID。

本次已登记 `YZ-CASE-20261019-001` → 页面Eval运行ID `9d94e3ea-3b07-4ced-b635-ac68a3038b96` → 内部简历Trace `42f131d8-92b6-448f-a3a7-5ce0f95f8798` → `ai-change-1792371107015-2`。两个Trace/运行编号都保留，避免误将页面运行编号与内部追踪编号当成同一字段；只存指针和反馈，不复制整份私人简历。机器可读登记见 `docs/architecture/evals/resume-case-feedback.json`。
