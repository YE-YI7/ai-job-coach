# 益职求职作战盘 V1 产品规格

> 状态：已确认方向，进入设计与实现
> 日期：2026-08-13
> 主分支：`backend`
> 产品名称：益职 AI
> 线上域名：<https://ai-job-coach.xin>

## 1. 产品定义

益职不是一个要求用户在聊天窗口里完成所有工作的“AI 求职聊天机器人”，也不是一组独立的简历、面试 Skills。

益职用同一套求职作战方法提供两个独立闭环的版本：付费网页版由益职提供模型、账号和云端作战盘；免费 Agent 版由用户自己的 Agent 提供模型，并在该 Agent 的本地沙箱中建立可视作战盘。两个版本共享方法与 Schema，但 V1 默认不共享用户数据。

“益职免费”仅表示益职不向 Agent 版收取模型费；用户的 Agent 宿主仍可能按套餐或用量计费。

网页主链路：

- 用户在网页直接新建岗位并提供 JD；
- 网页完成岗位判断、证据核对和下一步规划；
- 用户在网页直接回答问题、审阅简历、练习面试和提交复盘；
- 所有结果更新同一个岗位机会。

Agent 免费版链路：

- 用户用一句自然语言让 Agent 阅读益职安装页；
- Agent 按宿主专用说明安装 Plugin，或安装 Skills + 本地 MCP，并完成验证；
- Agent 在新会话中创建一个真实的岗位机会；
- 益职作战盘在 Agent 沙箱中启动，并通过本机 `127.0.0.1` 链接在内置浏览器或普通浏览器中打开；
- Agent 通过本地 MCP 持续更新机会、证据、简历、面试和任务；
- 除非用户未来明确选择同步，Agent 版不会向益职云端上传求职数据。
- 用户在网页中阅读、确认、修改和推进，不必在对话里消费大量长文本。

一句话定位：

> 把从看到 JD 到拿到 Offer 的全过程，变成一个用户可见、可编辑、可持续推进的岗位作战盘。

## 2. 为什么现在的产品形态不成立

当前版本以职业阶段和聊天页面为主要结构，存在四个根本问题：

1. **聊天不是好的工作台**：长分析消耗 token，难比较、难回看、难编辑。
2. **阶段彼此割裂**：JD 分析、简历修改、模拟面试和复盘没有围绕同一个岗位连续演化。
3. **Skill 缺少产品结果**：规定 Agent 如何回答，并没有让 Agent 操作一份用户可见、可接管的项目。
4. **通用 Agent 足以替代**：如果交付仍是一段文字，用户直接问 ChatGPT、Claude 或 Codex 即可。

新版本必须把产品顶层对象从“聊天阶段”改为“岗位机会”。

## 3. ChatCut 式产品模型

益职借鉴 ChatCut 的不是视频功能，而是产品结构：

| ChatCut | 益职 |
| --- | --- |
| 视频项目 | 岗位机会 |
| 素材库 | 个人经历证据库 |
| 时间线 | 求职推进记录 |
| 片段和轨道 | JD 要求、证据、简历版本、面试片段 |
| 在线编辑器 | 网页求职作战盘 |
| MCP 修改项目 | MCP 更新机会数据与产物 |
| 导出视频 | 导出简历、面试作战书、复盘报告 |

产品闭环：

```text
网页新建岗位 → 收录 JD 与真实经历 → 证据化判断 → 用户在页内继续推进

Agent 版：一句话安装 → Plugin 或 Skills + 本地 MCP 验证 → Agent 读取本地材料 → 更新本地作战盘
```

## 4. 目标用户

### 4.1 首批用户

- 正在主动求职或准备跳槽；
- 同时跟进 3 个以上岗位；
- 已经会使用 ChatGPT、Codex、Claude Code 或 WorkBuddy；
- 手上有简历、JD、面试记录等文件；
- 对“每次重新解释自己”和“AI 输出泛泛而谈”有明显不满。

V1 优先服务 AI 原生的技术、产品、运营、设计等知识工作者，不以完全不会使用 Agent 的大众用户为首要目标。

### 4.2 核心任务

用户雇佣益职不是为了“聊职业”，而是为了：

> 管清楚自己正在争取哪些机会，并在今天完成最能提高拿到 Offer 概率的动作。

## 5. 产品原则

1. **岗位机会是唯一主线**：所有分析和产物必须归属于一个岗位机会。
2. **网页承载复杂信息**：对话只保留确认、进度和下一步，不倾倒完整报告。
3. **网页独立可用，Agent 可选执行**：网页不得把“复制给 Agent”作为核心任务的完成方式；Agent 可整理和建议，不替用户确认未经证实的经历与数字。
4. **一次输入，多阶段复用**：JD、简历和证据只处理一次，后续阶段直接继承。
5. **先展示证据，再给结论**：禁止只有匹配分，没有可追溯依据。
6. **下一步必须明确**：任何页面和 Agent 调用结束后，都应给出一个具体下一动作。
7. **主动但不骚扰**：心跳只在确有风险、截止时间或缺失信息时触发，并允许静默。
8. **本地材料最小上传**：默认只同步完成任务所需的结构化结果；原始文件上传需要明确说明。

## 6. 信息架构

### 6.1 两个顶层对象

#### 个人证据库 Candidate Evidence Library

保存用户可复用的真实信息：

- 工作经历；
- 项目经历；
- 技能；
- 结果指标；
- STAR 故事；
- 可证明材料；
- 用户确认状态；
- 信息来源。

#### 岗位机会 Opportunity

保存一份具体机会从发现到结束的完整状态：

- 公司与岗位；
- 原始 JD 快照；
- 要求拆解；
- 证据匹配与缺口；
- 投递判断；
- 定制简历版本；
- 沟通记录；
- 面试安排与作战计划；
- 模拟面试；
- 真实面试复盘；
- 任务、截止时间与最终结果。

### 6.2 作战盘页面结构

桌面端采用三栏布局：

```text
┌ 机会列表 ─────┬ 当前岗位工作区 ─────────────────┬ 今日行动 ─────┐
│ 字节 AI PM    │ 公司 / 岗位 / 阶段 / 风险       │ 下一步         │
│ 美团策略产品  │ 概览 证据 简历 面试 复盘 动态   │ 待确认问题     │
│ 腾讯产品运营  │                                 │ 截止提醒       │
│ + 新建机会    │ 当前标签页的详细内容             │ Agent 动态      │
└───────────────┴─────────────────────────────────┴───────────────┘
```

固定标签页：

1. **概览**：当前判断、阶段、关键风险、进度、近期事件。
2. **JD 与证据**：要求、证据强弱、缺口、待确认事实。
3. **简历**：基础简历、岗位版本、差异与事实来源。
4. **面试**：面试安排、预测问题、训练计划、模拟记录。
5. **复盘**：真实问题、回答表现、决定性片段、改进任务。
6. **动态**：Agent 和用户对该机会的所有操作记录。

右侧“今日行动”跨标签页保持可见，避免用户看完报告却不知道做什么。

移动端按“机会 → 今日行动 → 当前标签内容”的顺序折叠，不复制桌面三栏。

## 7. V1 功能规格

### F1. 一键收岗位

用户把 JD 链接、文字、截图或文件交给 Agent，Agent 创建岗位机会并保存 JD 快照。

必须做到：

- 自动提取公司、岗位、地点、薪资、截止时间；
- 无法确定的字段标记为“待确认”，不得猜测；
- 保存原始来源和抓取时间；
- 相同公司和岗位疑似重复时先提示合并；
- 职位下架后仍可查看快照；
- 创建成功后立即返回作战盘 URL 并打开。

### F2. 值不值得投

系统必须给出三档建议：

- 优先投递；
- 补充后投递；
- 暂不投入。

判断页面必须展示：

- JD 核心要求；
- 对应用户证据；
- 证据等级：强、弱、无、待确认；
- 硬门槛与可弥补缺口；
- 结论理由；
- 下一动作。

匹配分只能作为辅助视觉，不能代替证据与解释。

### F3. 个人经历证据库

用户第一次提供简历后，Agent 提取候选证据；后续岗位直接复用。

每条证据必须包含：

- 内容；
- 类型；
- 来源文件或用户回答；
- 适用技能和岗位要求；
- 是否经用户确认；
- 最后使用时间。

以下内容必须经过用户确认才能成为“已确认事实”：

- 数字指标；
- 团队规模；
- 职级和职责边界；
- 项目归属；
- 商业结果。

### F4. 一岗一版简历

每个岗位机会拥有独立的简历版本，不能覆盖用户基础简历。

页面提供：

- 原文与建议文案对照；
- 修改理由；
- 对应 JD 要求；
- 对应真实证据；
- 待确认事实；
- 接受、拒绝、手动编辑；
- 版本历史与回滚；
- DOCX/PDF/Markdown 导出。

任何无法追溯到证据库的新增事实都必须阻止导出或明确警告。

### F5. 面试作战页

面试前用户只需打开一个页面即可准备当前岗位。

页面包含：

- 面试时间、轮次、面试官信息；
- 岗位最可能考察的能力；
- 简历中最容易被追问的表述；
- 证据不足的风险点；
- 预测问题和追问链；
- 用户准备好的故事；
- 仍需完成的训练任务；
- 面试前 30 分钟精简清单。

### F6. 针对性模拟面试

模拟面试必须基于当前岗位的 JD、简历版本和风险，不使用通用随机题库作为主流程。

要求：

- 一次只问一个问题；
- 根据回答继续追问；
- 优先攻击弱证据和夸大风险；
- 明确区分内容、结构、表达三个维度；
- 结束后把问题和训练任务写回当前岗位；
- 不在聊天中输出冗长总报告，只给摘要和作战盘入口。

### F7. 面后快速复盘

用户可以提供录音、转写或回忆。系统在 10 分钟内形成可编辑复盘。

输出包括：

- 面试问题地图；
- 每题回答摘要；
- 决定性表现；
- 未回答或失分问题；
- 面试官释放的信号；
- 下一轮准备项；
- 对证据库、简历和岗位判断的更新建议。

用户只提供零散回忆时，系统应主动逐步追问，不要求用户先整理完整材料。

### F8. 多岗位优先级与心跳

系统每天根据以下信号计算行动优先级：

- 投递或面试截止时间；
- 面试临近程度；
- 当前机会价值；
- 用户匹配度和成功概率；
- 待办所需时间；
- 多久没有推进；
- 是否等待外部回复。

作战盘给出“今天最值得做的三件事”，而不是展示所有待办。

#### 主动提问

出现以下情况时允许主动提问：

- 结论依赖一个尚未确认的关键事实；
- 面试临近但关键故事尚未准备；
- 用户标记“已面试”但没有复盘；
- 岗位长时间停滞且没有下一步；
- HR 沟通需要用户决定；
- 截止时间或面试时间存在冲突。

提问规则：

- 一次只问一个最有价值的问题；
- 说明为什么现在问；
- 尽量提供可快速选择的答案；
- 用户连续忽略两次后，七天内不再就同一事项提醒；
- 用户可对单个机会静音，或关闭全部主动提醒。

#### 心跳机制

心跳不是让模型持续空转，而是由事件与定时扫描产生结构化提醒。

触发方式：

1. **事件心跳**：创建机会、上传简历、变更面试时间、完成模拟、面试结束等事件后立即评估。
2. **日常心跳**：每天一次扫描活跃机会，生成最多三条行动。
3. **临近心跳**：面试前 24 小时和 2 小时检查准备缺口。
4. **停滞心跳**：机会超过设定天数未更新时询问状态。

交付通道按能力降级：

- 宿主支持后台任务/通知：向对应 Agent 任务发送提醒；
- 宿主只支持会话启动：用户下次打开 Agent 时由 Plugin 拉取提醒；
- 网页：在今日行动和通知中心展示；
- 邮件等外部通知不属于 V1 默认能力，需用户单独订阅。

### F9. 招聘沟通助手

基于当前机会生成：

- 首次打招呼；
- 补充材料；
- 确认面试；
- 修改时间；
- 面试后跟进；
- 询问进度；
- 谈薪；
- 婉拒。

系统必须继承当前岗位、用户语气和已有沟通历史。发送行为必须由用户确认；V1 默认只生成和复制，不自动对外发送。

### F10. 跨阶段自动贯通

这是横向基础能力，不是单独页面。

- JD 的重要要求自动成为简历覆盖目标；
- 简历中强化的内容自动进入面试追问清单；
- 模拟面试暴露的问题自动生成训练任务；
- 真实面试反馈自动更新风险与证据；
- 多次机会中重复出现的弱项进入个人长期训练清单；
- Offer 或拒绝结果回写本次机会，但不得用单次结果直接推断用户长期能力。

## 8. 安装与启动体验

### 8.1 用户入口

官网首页先提供两个版本入口；Agent 免费版统一进入一份可由人和 Agent 阅读的执行手册：

- `/agent`：识别与选择 Agent；
- 同一页包含 Codex、Claude Code、WorkBuddy 和通用 MCP 宿主的分支。

用户看到的是简短的价值说明、演示和“一键复制安装提示”。

Codex 中文安装提示示例：

```text
请打开并完整阅读 https://ai-job-coach.xin/agent，按页面说明安装益职免费版，并验证本地求职作战盘可以打开。
```

### 8.2 Agent 执行手册

同一 URL 对 Agent 抓取返回纯文本执行说明，对正常浏览器导航返回可视化页面。执行说明必须：

- 首先识别宿主和本地/远程环境；
- 要求 Agent 完整阅读后再执行；
- 给出安装、宿主 MCP 注册、验证的精确顺序；
- 明确哪些步骤必须等待用户完成；
- 失败时继续诊断，不得虚报完成；
- 解释新装 Plugin 只能在新会话加载；
- 尽可能自动创建并切换到新会话；
- 最终新会话必须包含第一个启动提示和已验证的本地作战盘链接；
- 使用版本化手册，保留升级与恢复路径。

### 8.3 第一次启动

新会话中的启动目标：

1. 验证益职 MCP 可用；
2. 简短说明益职能完成的任务；
3. 创建“我的第一个求职机会”或根据已有 JD 命名；
4. 打开内置浏览器中的作战盘；
5. 只询问开始下一步所需的最少材料。

成功标准不是“插件已安装”，而是用户已经看到第一个可操作的作战盘。

## 9. Plugin 规格

### 9.1 Plugin 的职责

- 把求职意图路由到益职本地 MCP；
- 读取用户明确提供的本地 JD、简历和面试材料；
- 根据工具 Schema 提交结构化数据；
- 打开或复用当前机会的作战盘；
- 在任务开始时读取待处理心跳；
- 在对话中只返回简短状态、关键问题和页面入口。

### 9.2 Plugin 不负责

- 把未经用户选择的求职材料同步到益职云端；
- 用 Skill 保存完整报告；
- 在每次对话加载全部求职方法；
- 直接连接数据库；
- 绕过用户确认上传所有本地文件。

### 9.3 宿主包

公共仓库至少包含：

```text
plugin/
├── codex/
│   ├── .codex-plugin/plugin.json
│   ├── .mcp.json
│   └── skills/
├── claude/
│   ├── .claude-plugin/plugin.json
│   ├── .mcp.json
│   └── skills/
├── workbuddy/
│   └── install assets / instructions
└── docs/
    ├── codex-install.md
    ├── claude-install.md
    └── workbuddy-install.md
```

共用业务语义，宿主安装、授权、浏览器交接和会话切换逻辑分别维护。

## 10. MCP 规格

### 10.0 当前发布边界

Agent 免费版 V1 使用本地 stdio MCP：状态与用户选择保存的产物位于 `~/.yi-zhi/`，可视作战盘只监听 `127.0.0.1`。下述远程 MCP 是未来可选的跨设备同步能力，不是免费版本上线和使用的前置条件。

### 10.1 未来远程同步的基础要求

- HTTPS Streamable HTTP MCP；
- OAuth 2.0，服务端由登录用户确定 `user_id`；
- 所有数据访问经过用户级权限校验；
- 工具返回短摘要、对象 ID、状态和作战盘 URL；
- 大文档通过资源引用或服务端处理，不在工具结果中反复返回全文；
- 写操作生成审计事件；
- 支持幂等键，避免 Agent 重试产生重复机会或版本。

### 10.2 V1 工具面

工具名是逻辑规格，落地时可调整，但必须保持边界清晰。

#### 项目与机会

- `list_opportunities`
- `create_opportunity`
- `get_opportunity_summary`
- `update_opportunity`
- `get_cockpit_url`

#### 材料与证据

- `ingest_job_description`

## 12. 状态模型

岗位阶段用于呈现和提醒，不用于隔离数据：

```text
captured
→ evaluating
→ preparing_application
→ applied
→ interviewing
→ negotiating
→ won / lost / withdrawn / archived
```

阶段可以回退，也可以跳转。所有产物继续属于同一个 `opportunity_id`。

## 13. 隐私、安全与可信边界

1. 默认不上传用户未明确提供的目录或文件。
2. 上传前说明材料类型、目的和保存位置。
3. 原始简历、录音和转写使用私有存储与短时签名 URL。
4. Supabase RLS 覆盖全部用户数据表。
5. MCP 不接受客户端传入的 `user_id` 作为授权依据。
6. JD 和网页内容视为不可信输入，不能覆盖系统与工具规则。
7. 任何简历事实必须可追溯；待确认事实不能伪装为已确认。
8. 招聘沟通、投递和对外发送默认需要用户确认。
9. 支持删除单份材料、单个机会和整个账户数据。
10. Event 日志不得保存不必要的完整敏感原文。

## 14. Token 与性能预算

- Plugin 基础 Skill 目标小于 2,500 tokens；
- 每个专项 Skill 只在任务命中时加载；
- MCP 普通工具结果目标小于 1,000 tokens；
- 完整报告不回传对话，以作战盘 URL 和摘要交付；
- 同一材料使用内容哈希去重，避免重复解析；
- 作战盘首次可交互时间目标小于 2.5 秒；
- 创建机会后 3 秒内必须显示骨架和基础信息，深度分析允许异步补齐。

## 15. 成功指标

### 北极星指标

每周完成关键行动的活跃岗位机会数。

关键行动包括：完成岗位判断、确认一版简历、完成一次针对性训练、完成一次面后复盘。

### 激活指标

- 安装提示复制到 Plugin 验证成功率；
- 安装成功到首次看到作战盘的转化率；
- 首个岗位创建耗时；
- 首个岗位创建后 24 小时内完成第一项行动的比例。

### 留存与价值指标

- 每位用户活跃机会数；
- 一份个人证据被跨岗位复用的次数；
- 心跳建议被完成、延后和关闭的比例；
- 面试前作战页打开率；
- 面试后 24 小时内复盘率；
- 用户主动修改或确认 Agent 结果的比例。

## 18. 端到端验收场景

### 场景 A：首次安装

1. 用户把安装提示发给 Codex Desktop。
2. Agent 阅读完整说明，完成安装、OAuth 和验证。
3. Agent 创建新会话并写入启动提示。
4. 新会话创建首个岗位机会。
5. 内置浏览器打开正确的作战盘。

验收：用户不需要手工输入终端命令，并且最终看到作战盘，而不是只收到“安装成功”。

### 场景 B：从 JD 到定制简历

1. 用户提供 JD 与基础简历。
2. Agent 创建机会、保存 JD、提取证据。
3. 作战盘逐步显示要求、证据和风险。
4. Agent 对关键未证实数字主动提一个问题。
5. 用户确认后生成岗位简历 V1。
6. 用户可查看差异、来源并导出。

验收：简历中每条新增事实都可追溯，完整报告不需要在聊天中展开。

### 场景 C：面试前后贯通

1. 用户把机会标记为已约面。
2. 系统根据 JD、简历和弱证据生成面试作战页。
3. 面试前 24 小时心跳发现一个未准备风险并主动提问。
4. 用户完成针对性模拟。
5. 面试后系统提示快速复盘。
6. 复盘结果更新风险、任务和证据库。

验收：所有数据保留在同一个机会中，用户无需重复上传或讲述背景。

### 场景 D：多岗位优先级

1. 用户拥有至少五个活跃机会。
2. 一场面试临近，一个岗位即将截止，三个岗位等待回复。
3. 日常心跳只生成最多三项行动。
4. 用户延后或静音后，不重复骚扰。

验收：行动排序有理由、可执行、不会无限增加通知。

## 19. 发布门槛

V1 对外发布前必须满足：

- 四个端到端场景全部通过；
- 权限与 RLS 审计通过；
- Agent 安装过程中任一步失败都不会虚报完成；
- 作战盘在桌面和移动端可用；
- 关键写操作有 Event 记录；
- 心跳支持去重、延后、静音；
- 线上错误率和首屏性能达到预算；
- 至少 5 位真实求职者用自己的材料走完单岗位闭环。

## 20. 已确认的产品决策

- 最大功能是 ChatCut 式“一句话交给 Agent + Agent 在自己的沙箱中建立可视作战盘”。
- 十项痛点功能全部纳入方向。
- 多岗位管理必须支持主动提问与心跳机制。
- 网页版与 Agent 本地版各自拥有完整可视界面，对话不是完整交付界面。
- Plugin 是宿主连接器，本地 MCP 是免费版操作层，岗位机会是产品主对象；远程 MCP 仅作为未来可选同步层。
- 旧七阶段聊天前端不再作为新版本的信息架构基础。
